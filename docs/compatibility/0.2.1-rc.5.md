## rc.4 → rc.5 source differences and seam survival

This bump required **no decoration change**, because rc.5 is again a **pure version-number republish**: it carries **no source change at all** relative to rc.4. All 70 installed `@deepseek-ai/dsh-*` packages were compared file-by-file by SHA-256 between the rc.4 tree in the parent checkout and the rc.5 tree installed for this adaptation (probe `.dsh-ops/rc5-compare.mjs`, 1280 files: 1209 byte-identical, 10.01 MB of identical content). The only differing files are:

1. each package's `package.json` (70 files, version fields only, all identical lengths), and
2. `@deepseek-ai/dsh-client-modules/lib/index.js`, where one embedded build-commit marker changes `ec17a2c` → `d4db512` at identical file length (42342 bytes, first difference at byte offset 24827) with no logic difference.

`node_modules/.bin` shims are excluded from the comparison by design: pnpm rewrites them with absolute store paths, so they always differ between two checkouts and carry no package logic.

The official Workspace Client is byte-identical between the two generations: **232824 bytes**, SHA-256 `9c2c17a66a5c20de00ac2852cb76debb5237439e97f877403bcaa2a471086544` — the same digest the rc.4 gate already pinned. The gate therefore moved only the *version* constants (`WORKSPACE_UI_VERSION` / `WORKSPACE_LOCALE_VERSION` in `scripts/workspace-sidebar-upstream.mjs:5-6`) while the SHA-256 constant stayed unchanged, which is a real check rather than an assumption: had the artifact differed, the gate would have rejected the build. The tarball digest was confirmed independently via `npm pack` (`106330` bytes) before the version constants moved.

All eight required text seams reach the derived source: `__dshGitWorktreeManagedGuard`, `dshGitWorktree.managed`, `dshGitWorktree.state.working`, `managedWorktreeDecoration`, `ManagedWorktreeIdentity`, `__dshGitWorktreeProtected`, `__dshGitWorktree`, `data-managed-worktree`. `visibleSessionMenuItems` is absent from upstream on every generation because that identifier is introduced *by the plugin's own decoration*; its seam is `replaceIfPresent` and its absence is the expected, unchanged case. The derived artifact is byte-identical to the rc.4 derivation (`derived bytes: 236427`, SHA-256 `9b3a2e6a49cef3b121df9c157efec4f5c36cede681199526495700b0111777f2`).

## Changes in this adaptation

1. `package.json` — 22 DSH dev dependencies moved from exact `0.2.1-rc.4` to exact `0.2.1-rc.5`; the locale peer enumeration gains `|| 0.2.1-rc.5`. The core peers' caret range `^0.1.2-rc.1 || ^0.2.0-rc.1 || ^0.2.1-rc.1` already covers rc.5, so no peer range change was needed there.
2. `pnpm-workspace.yaml` — `minimumReleaseAgeExclude` gains the 70 matching `@deepseek-ai/...@0.2.1-rc.5` entries, mirroring the existing rc.4 block.
3. `scripts/workspace-sidebar-upstream.mjs:5-6` — `WORKSPACE_UI_VERSION` and `WORKSPACE_LOCALE_VERSION` moved to `0.2.1-rc.5`; `WORKSPACE_CLIENT_SHA256` deliberately unchanged (byte-identical artifact).
4. `src/host-compat.ts:12-22` — the modern-generation comment now records rc.5 as the pinned modern release and states the byte-identical Workspace Client evidence. No logic change: `0.2.1-rc.5` resolves to `modern` through the existing `isModernGeneration` predicate.
5. `tests/host-compat.test.ts` — the locale-peer assertion gains `|| 0.2.1-rc.5`, and the pinned-flavor case list gains `0.2.1-rc.5` → `modern`.

## Residual risks

- The decoration path still relies on exact text seams in the official compiled Client. Each upstream bump requires re-running the version/SHA gate and the seam probe; a silent seam drift fails closed at build time, not at runtime. A version-number-only republish like rc.5 is the *best* case, not a reason to skip the probe next time.
- Compatibility was exercised on Windows only. The macOS-only cases (newline-in-path identity reads, executable-bit resource preservation) did not run here.
- Passing build and unit tests on rc.5 packages is source compatibility, not runtime acceptance on a launched Host.
- `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude` list is maintained by hand per DSH release; a future bump that forgets it will surface as an install-time minimum-release-age rejection rather than a silent version mix, but the list is still a manual bookkeeping cost.
